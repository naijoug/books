# AI Agent 失败吸收一页纸

用于无人值守、周期性唤醒或 dirty workspace 接力场景：当工具输出失败、测试失败、搜索无结果、依赖缺失或 repo 边界不清时，Agent 不能只把失败写进日志；必须让失败改变本轮计划。

## 1. 先把失败变成一句可操作事实

写成“信号 -> 影响 -> 证据位置”，不要写成情绪或猜测。

```text
失败信号：<命令/检查/搜索> 输出 <关键失败摘要>。
影响判断：这会影响 <范围/顺序/目标/交接>。
证据位置：<命令、文件、日志或状态快照>。
```

例子：

```text
失败信号：git status --short 显示候选 repo 启动前已有 staged/unknown path。
影响判断：目标切换；本轮不接管该 repo，改选 clean 的项目 repo 做独立小任务。
证据位置：启动快照和收尾 status。
```

## 2. 四类最小改计划

| 失败信号 | 改变什么 | 最小动作 | notebook 必写 |
|---|---|---|---|
| 全量测试失败，堆栈落在启动前 dirty 模块 | 范围缩小 | 只验证并提交本轮文档或当前 path；代码测试失败列为未接管边界 | “因测试落在启动前 dirty 模块，本轮范围缩小为 ...” |
| `diff --check` 或格式检查失败 | 顺序变更 | 先修格式并重跑检查，再做结构断言、stage、commit | “先修复格式失败，再继续提交链路” |
| 候选 repo 启动前 staged/unknown，归属不明 | 目标切换 | 不接管该 repo；切到 clean 项目 repo 或只读观察 | “目标从 ... 切换到 ...，原因是启动前边界不清” |
| 依赖缺失、网络不可用或环境无法安装，导致验证无法执行 | 交接改写 | 不写“已验证”；最终报告列未验证项，后续接力给第一条命令和所需依赖 | “验证未完成；下一次先运行 ...，需要 ...” |

## 3. 决策顺序

1. 先判断失败是否来自本轮改动。
2. 如果来自本轮改动：优先修复、回滚或缩小到可验证部分。
3. 如果来自启动前 dirty / staged / unknown path：不要扩大接管范围，把它写入未接管边界。
4. 如果来自环境或依赖：尝试一个低风险替代验证；仍不可验证时，显式交接。
5. 最终报告必须写出失败如何改变了范围、顺序、目标或交接。

## 4. 可复制 notebook 句式

```text
- 实际推进：原计划是 <原计划>；因 <失败信号>，本轮将 <范围/顺序/目标/交接> 调整为 <实际选择>，并只推进 <可验证小块>。
- 验证方式：<已成功的命令/检查>；<失败命令> 未作为完成证据，原因是 <失败归属或环境限制>。
- 后续接力：下一次先 <第一条命令或检查>；若 <边界条件> 仍存在，则继续不接管 <path/repo>，改选 <备选路径>。
```

## 5. 收尾检查

- 每条关键失败输出是否至少改变了范围、顺序、目标或交接中的一项？
- notebook 是否保留失败信号、影响判断和证据位置？
- 最终报告是否区分“已验证成果”和“失败导致未验证/未接管边界”？
- 如果本轮切换目标，是否写明原目标为什么不适合继续推进？
- 如果验证不可执行，是否给出下一轮第一条命令和依赖，而不是只写“待验证”？

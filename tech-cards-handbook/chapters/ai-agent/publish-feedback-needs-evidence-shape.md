# 发布反馈先看证据形状，不要只看互动量

## 问题

AI 编程审查样本征集发出去以后，最容易被点赞、收藏、转发和“这个有用”带偏。互动量能说明 hook 是否被看见，却不能说明有人愿意交出真实代码证据、接受只读审查或为下一步交付付费。

更可靠的做法是把每条反馈先记录成证据形状：对方给的是 PR、失败命令、agent log、final report、review comment，还是只有泛泛认可。只有证据形状和公开边界足够清楚，才进入 `Continue / Narrow / Stop` 决策。

## 要点

- **先抄原话，不先解释需求**：记录对方的具体痛点原话，再判断它支持的是 `Fact`、`Inference` 还是 `Unverified`。
- **每条反馈必须有证据形状**：PR、失败命令、agent log、final report、review comment 都比“我们也遇到过”更接近真实需求。
- **公开边界和下一步一起问**：是否允许匿名复盘、哪些路径/客户名/日志必须排除，决定这条反馈能否转成案例或只能内部学习。
- **互动量只作为 hook 信号**：点赞多但无人补证据，说明标题可能吸引人；不能据此写成产品需求或成功案例。
- **决策必须收口**：`Continue` 进入首份报告，`Narrow` 缩到一条命令或一个文件，`Stop` 停止公开和交付承诺。

## 示例

```text
发布反馈记录：
- 原话："AI 改完后 CI 挂了，但没人知道该先回滚哪块"
- 证据形状：失败命令 + exit code，暂时没有 PR
- 公开边界：可匿名；不能出现客户名、仓库名和绝对路径
- 当前判断：Narrow
- Next evidence needed：补 CI 命令、失败片段、最近一次 agent summary
- 可沉淀资产：下一条安全命令梯样例；暂不写公开案例
```

```text
判断：
- Continue：对方给出 PR / log / final report，并接受只读范围和公开边界。
- Narrow：只有一个失败命令、一个 review comment 或一段 handoff，先交付单点判断。
- Stop：只有点赞、收藏、泛泛认可，或必须拿生产权限、密钥、未脱敏私有数据才能判断。
```

## 坑

- **把点赞当购买信号**：点赞说明内容被看见，不说明对方愿意提供证据、预算或授权。
- **把模糊共鸣写成案例**：没有 PR、命令、log 或 review comment 时，只能标 `Unverified`，不能包装成战报。
- **忽略公开边界**：对方给了真实材料，也不等于能公开；涉及 `Private` 信息时先删减、脱敏或 `Stop`。
- **过早改 offer**：一次模糊回复不足以改产品定位；先问 `Next evidence needed`，再决定是否 `Narrow`。
- **把观察表变成复盘散文**：观察记录必须保留原话、证据形状、公开边界和下一步，不要只写“反馈不错”。

## 检查

复盘一次发布反馈前检查：是否记录了具体痛点原话；是否写清证据形状；是否标出 `Fact`、`Inference`、`Unverified`、`Private` 或 `Stop`；是否写了公开边界和 `Next evidence needed`；是否用 `Continue / Narrow / Stop` 收口；是否把点赞、收藏和转发单独放在 hook 信号里，而不是当成真实需求。若任一项缺失，先补证据，不要写案例、承诺咨询或开始产品化。

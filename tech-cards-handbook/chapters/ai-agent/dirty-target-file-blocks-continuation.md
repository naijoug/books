# 目标文件已有改动时，先确认归属和授权范围

## 问题

上一轮接力点指向的文件已经有未提交改动。什么时候可以继续修改，什么时候只暂停受影响部分？

## 要点

- `dirty` 只表示有未提交差异，本身不代表冲突或缺少授权。先读相关 diff，结合当前用户要求和交接证据判断。
- 归属与范围明确、能保留已有改动时，可以继续原任务；当前会话产生的改动、可追溯的上一轮交接和用户明确授权都可以作为依据。
- 来源不明或修改会与已有 diff 冲突时，对受影响部分保持只读；记录缺少的证据或需要解决的冲突，继续原任务内独立且已授权的工作。
- 是否可以编辑与是否可以提交分别判断。获准修订某文件，不等于可以把它的全部历史 diff 纳入本轮 commit；提交前核对实际 staged diff。
- `clean replacement` 仅适用于用户已授权跨项目选题的任务。指定目标受阻时，不为了保持产出自动换仓库、新增卡片或扩写模板。

## 示例

```text
目标：继续修复章节中的引用。
启动状态：目标 Markdown 已修改。
证据：用户明确要求基于当前稿修订，diff 是待保留的结构调整。
决策：保留结构调整，只更新所需引用并运行引用格式检查；不因 dirty 再问一次是否继续。
提交边界：任务未要求提交，本轮只交付修改与验证结果。
```

遇到未知改动时：

```text
目标：修改 A、B 两个文件。
启动状态：A 的目标段落有来源不明且与本次方案重叠的 diff；B 可独立修改。
决策：A 标为 blocked continuation，先只读 intake；继续完成 B 及相关验证。
回归条件：确认 A 的改动来源和保留方案后恢复。原目标仍是 A、B，不切到别的仓库写卡片。
```

## 坑

- 只凭 `git status` 中的 `M` 就停止整个任务，或把无关仓库的 clean 状态当作换目标理由。
- 只凭上一轮接力文字就覆盖未知 diff；没有检查当前内容和授权范围。
- 编辑授权与提交授权混为一谈，把用户已有改动描述成本轮成果。
- 为通过收尾模板而扩大任务或创建与原目标无关的流程文档。

## 检查

能否说明已有改动的来源、本次授权范围、保留方案，以及实际暂停的是哪一部分？明确可继续的部分是否已完成并验证？如有提交，staged diff 是否与本次允许纳入的内容一致？

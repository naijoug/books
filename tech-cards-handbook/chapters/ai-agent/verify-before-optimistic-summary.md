# 验证先于乐观总结，不要把“看起来完成”当完成

**问题**：Agent 完成一次修改或资料整理后，为什么容易在报告里写“已完成”“已解决”，但下一轮才发现构建没跑、索引没同步、或改动根本没有落到目标文件？

**要点**：

- 总结之前先验证：任何“已完成”都应该对应一个可复核证据，例如命令输出、文件读取、计数脚本、diff 边界或人工检查标准。
- 验证失败时不要润色成成功报告；先把失败事实写出来，再决定修复、缩小范围或交接。
- 报告要区分三类话：`已验证的事实`、`合理推断`、`下一步假设`，不要把推断写成事实。
- 对短节拍任务，验证链路不必复杂，但必须能回答：改了什么、怎么知道它生效、还没验证什么。

**示例**：

```text
错误总结：
- 已完成日志过滤优化，应该可以正常使用。

更好的总结：
- 已修改 `loom/src/components/Workspace/DebugPane.tsx`，新增日志过滤命中数。
- 验证：`npm run build` 通过；`cargo check --manifest-path src-tauri/Cargo.toml` 通过；`git diff --check` 无 whitespace error。
- 未验证：没有做浏览器手工点击 next/prev，因为本轮没有实现跳转交互。
- 下一步：如果继续增强日志过滤，先评估跳转是否会引入 DOM refs 和滚动状态。
```

**坑**：

- 用“应该”“看起来”“理论上”替代验证结果，导致交接读者无法判断可信度。
- 只验证最容易通过的部分，例如只跑格式检查，却声称功能已经完整可用。
- 工具失败后继续按原计划总结，把失败输出当成不重要噪音。
- 为了显得进展顺利，省略未验证项，下一轮只能重新摸索边界。

**检查**：在最终总结或 notebook 里，每一句“已完成/已修复/已同步”旁边都能找到证据；如果找不到，就改写为“已尝试”“已修改但未验证”或继续补一条低成本验证。

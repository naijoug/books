# 有效反馈才触发修订，不要被每个声音牵着走

**问题**：Agent 或开发者持续收到用户意见、评审评论和测试信号时，如何判断哪些反馈应该进入下一版修订，哪些只需要记录观察？

**要点**：

- 反馈先分级：`记录`、`观察`、`验证`、`修订`，不要收到一句话就改产品或代码。
- 能触发修订的反馈至少满足一个条件：可复现、多人独立出现、来自目标用户、影响核心任务、或有付费/留存/故障等行为证据。
- 单点反馈默认进入观察池；只有补到样本、复现步骤或业务影响后，才升级为修订任务。
- 修订必须写清“改什么、不改什么、成功标准是什么”，避免把反馈处理变成无限返工。

**示例**：

```text
输入反馈：
- 试读者 A：卡片不错，但不知道怎么在团队里用。
- 试读者 B：希望有更多 Agent 工具示例。
- 测试：`handoff` 示例里缺少下一步动作字段。

分级：
- A：观察。目标用户，但只有 1 人提到；下一轮外联继续问团队落地场景。
- B：记录。需求清晰，但不确定是否影响购买或使用；先放入候选卡片池。
- 测试：修订。可复现且违反卡片规则；补上下一步动作字段并跑检查。

修订任务：
- 修改 `handoff` 示例，确保每个交接样例包含 `next_action`。
- 成功标准：检查脚本能找到字段；人工复核示例仍然短小可读。
```

**坑**：

- 把“声音最大的人”当成目标用户，导致路线被非核心场景带偏。
- 把所有反馈都排进待办，结果真正影响收入、可靠性或学习路径的问题被淹没。
- 只写“根据反馈优化”，不写触发条件和成功标准，下一轮无法判断是否完成。
- 为了显得响应快而频繁改定位，破坏样品包、文档或系统接口的一致性。

**检查**：每个修订任务都能追溯到至少一条有效反馈，并写出触发条件、修改边界和验证标准；达不到这些条件的反馈只进入观察池或候选池。

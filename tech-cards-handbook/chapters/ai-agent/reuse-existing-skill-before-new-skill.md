# 先复用已有技能，不要把每条观察都写成新技能

## 问题

AI 编程审查或心跳工作流跑久以后，Agent 很容易把每次新观察都沉淀成一个新 skill：一次 CI 失败写一个 skill，一次发布反馈写一个 skill，一次客户问法再写一个 skill。短期看像是在积累资产，长期会让技能目录变成难以选择的碎片库，下一轮仍然不知道该先用哪个入口。

更稳的做法是：先把观察放进已有技能链路里跑一遍，确认它到底缺的是下一条安全命令、证据公开边界、结果记录字段，还是一个真正可重复的新流程。只有当同一类观察重复出现、输入输出稳定、验证标准明确时，才值得新增技能。

## 要点

- **观察先进入旧入口**：能用 `next-safe-command-ladder` 解决“下一步做什么”，就不要新建“CI 失败处理技能”；能用 `audit-evidence-boundary` 判断公开边界，就不要新建“案例发布技能”。
- **技能化门槛是重复性，不是新鲜感**：至少看到两到三条相似观察，且都需要同一组输入、输出和停止条件，再考虑抽象。
- **先写调用路径，再写技能正文**：新观察应该先回答“从哪个现有 skill 进入、产出什么中间结果、再交给哪个 skill”，而不是直接扩成完整流程。
- **保留 `Narrow` 状态**：证据不足时，把观察留在文档或日志里，标出 `Next evidence needed`；不要为了显得有沉淀而强行 `Continue` 成新 skill。
- **新 skill 必须减少选择成本**：如果新增后下一轮需要在三个相近技能之间猜入口，它就是负资产；如果能合并旧步骤、缩短判断路径，才是资产。

## 示例

```text
观察：
- 痛点原话："AI 改完后 lint 挂了，但不知道该先看 diff 还是先跑全量测试。"
- 证据形状：失败命令 + 一段 agent summary；没有完整 PR。
- 当前判断：Narrow。

复用路径：
1. 先进入 next-safe-command-ladder：
   - 当前最大风险：不知道失败是否来自本轮改动。
   - 下一条安全命令：只跑 lint 对应的最小目标，若失败再读本轮 touched files。
2. 再进入 audit-evidence-boundary：
   - Fact：已有失败命令和 exit code。
   - Inference：可能由本轮 agent 改动引入。
   - Private：仓库名、绝对路径、客户名不公开。
3. 最终决策：继续 Narrow，不新建技能。
   - Next evidence needed：完整 PR diff、最小复现命令、最近一次通过的基线。
```

只有当这种“lint 失败后不知道下一条安全命令”的样本在多个 repo 重复出现，并且每次都需要同一张输入表、同一组命令梯和同一套报告字段时，才把它升级为新 skill。升级前，先把它写进文档演示或书稿卡片，观察下一轮是否真的会复用。

## 坑

- **把一次案例写成技能**：一次脱敏样例只能证明你会描述流程，不能证明流程值得复用。
- **技能名越写越细**：`ci-lint-failure-after-agent-edit` 这类名字看似精准，实际会让调用者不知道它和通用命令梯的边界。
- **跳过现有技能**：不先复用已有入口，新增技能很可能只是旧 skill 的改名版。
- **没有停止条件**：如果 skill 只告诉下一轮“继续调查”，没有 pass/fail、`Narrow/Stop` 或公开边界，它会制造更多未验证工作。
- **把内容资产误当执行资产**：文章、案例、卡片可以解释原则；skill 必须能指导下一条动作并被验证。

## 检查

准备新增技能前先检查：这条观察是否已用现有技能跑过一遍；是否至少有两条相似样本；输入、输出、停止条件和验证方式是否稳定；新增技能是否会减少而不是增加入口选择；是否能写清它复用或替代哪些旧 skill；是否保留 `Next evidence needed` 和 `Continue / Narrow / Stop` 决策。任一项缺失时，先把观察放进文档、书稿卡片或样例，不要创建新技能。

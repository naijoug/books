# 短节拍任务不要变成重构

**问题**：每 15 分钟或每小时唤醒一次 Agent 时，如何避免一个小改动被扩展成重构、调研或大范围整理？

**要点**：

- 先给本轮定义“可提交的最小完成物”：一个文件、一张卡片、一个测试、一个小交互，而不是一个方向。
- 选择任务时同时写出停止线：哪些改动一旦出现，就说明本轮应该停下并记录为后续设计。
- 如果需要新增跨模块状态、迁移数据结构、改构建链路或做长时间调研，默认已经超过短节拍边界。
- 短节拍不是拒绝大任务，而是把大任务切成能验证、能提交、能交接的小块。

**示例**：

```text
目标：改进日志过滤体验。
本轮最小完成物：只显示命中总数。
停止线：不引入滚动定位、DOM refs、键盘快捷键或匹配索引状态。
验证：前端 build 通过，摘要文案可人工检查。
后续：next/prev 跳转单独设计。
```

**反例 / 修正做法**：

```text
反例：
- 本轮原本只想给日志面板补一个“复制当前筛选结果”按钮，但顺手把过滤状态、滚动定位、快捷键和布局样式都一起重构；最后没有稳定提交，也说不清哪些失败来自本轮按钮。

修正：
- 本轮最小完成物：只在 `loom/src/components/Workspace/DebugPane.tsx` 增加复制按钮，并复用已有过滤结果。
- 停止线：不改全局状态、不新增滚动定位、不调整布局 CSS、不设计快捷键。
- 验证：运行与该文件相关的最小前端检查；若发现复制能力需要新增跨组件状态，本轮停止在设计交接，不继续写实现。
```

**坑**：

- 用“顺手”作为理由继续扩展范围，最后既没有稳定提交，也没有可复核验证。
- 把重构伪装成小任务，例如“顺便整理一下组件结构”。
- 只记录做了什么，不记录本轮明确没有做什么，导致下一轮重复进入同一个范围膨胀。

**检查**：本轮结束时，能否用一句话说清“完成物是什么”和“哪些事被刻意留到后面”？如果不能，说明任务边界还不够短。

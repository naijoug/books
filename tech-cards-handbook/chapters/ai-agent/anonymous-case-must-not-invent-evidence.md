# 匿名案例不能编造证据，不要把样板写成战报

## 问题

AI 编程审查、自动化重构、Agent 工作流这类服务很适合写匿名案例：它比纯教程更可信，也比客户原始材料更安全。但很多案例在脱敏时会滑向另一个风险：为了让故事完整，补上没有发生过的指标、客户画像、故障原因和收益数字。

匿名案例的价值不是“看起来像真实战报”，而是让读者看到一条可复核的证据链：输入边界是什么、做了哪些检查、哪些结论有命令或记录支撑、哪些仍然只是未验证风险。

## 要点

写匿名案例前先分三层材料：

| 层级 | 可以写 | 不能写 |
|---|---|---|
| 事实 | 已授权的场景、变更类型、命令输出摘要、报告结构 | 客户名、仓库名、私有代码、未经授权截图 |
| 推断 | 基于证据的风险判断、为何先查某条路径 | 把猜测写成根因、把单次现象写成普遍规律 |
| 结果 | 已发生的修复、已通过的验证、客户明确反馈 | 虚构收益数字、虚构转化、虚构“上线后零事故” |

最小规则：

1. **先写证据边界**：案例开头说明来自什么类型的审查、哪些材料已脱敏、哪些内容被合成或省略。
2. **每个结论都能回到证据**：风险排序要能指向命令、diff、日志、截图描述或人工检查项。
3. **没有证据就写成未知**：不要为了案例好看补全 `before / after` 指标；把它放进 `Unverified` 或 `Next evidence needed`。
4. **脱敏不等于改编**：可以替换命名和删除敏感细节，但不要改变因果链和验证结果。

## 示例

不要这样写匿名案例：

```text
某 SaaS 客户的 AI 生成 PR 导致线上故障。我们审查后把构建时间降低 40%，上线后 30 天零事故。
```

如果没有客户授权、线上故障记录和 30 天指标，这段就是编造。更安全的写法是：

```text
案例来源：一次已授权脱敏的 AI 生成 PR 审查；仓库名、业务名和文件名已替换。
输入范围：1 个状态管理重构 PR、3 个相关 reducer/selector 文件、现有 unit test。
最高风险：AI 把 loading/error 分支合并后，空状态与错误状态可能被 UI 误判。
证据：focused reducer test 复现了 error branch；typecheck 通过；未执行浏览器 smoke。
建议：先补 reducer 分支测试，再用一个最小 UI smoke 验证错误态渲染。
Unverified：未检查真实生产数据、权限边界和跨浏览器行为。
```

这段不需要暴露客户，也没有假装已经证明所有收益；它把匿名案例变成可接力的证据摘要。

## 坑

- **把模板字段当事实填满**：模板里有 `Impact`、`Result`，不代表每次都必须写数字；没有证据就写“未观测”。
- **把公开样板伪装成真实客户案例**：mock report 可以作为样板，但发布时必须标注是示例，不要暗示来自客户项目。
- **脱敏后丢掉验证链**：只剩“我们发现问题并修复”，读者无法判断方法是否可复用。
- **把 AI 生成摘要当证据**：AI 的总结只能帮助组织材料，不能替代命令输出、diff、issue、PR 评论或用户原话。
- **遗漏停止条件**：如果案例涉及生产权限、密钥、合规或未授权代码，正确动作是停止发布或继续脱敏，而不是继续美化故事。

## 检查

发布匿名案例前，用这 6 个问题复核：

1. 是否明确写出 `Case source` 或“案例来源”，区分真实脱敏、合成样例和公开项目复盘？
2. 每个风险结论是否能指向至少一条证据，而不是只来自印象？
3. 是否把无证据的收益、转化率、事故率和客户反馈删掉或标为未验证？
4. 脱敏是否只替换身份信息，没有改变因果链、命令结果和验证范围？
5. 是否保留 `Unverified` / `Next evidence needed`，让读者知道还不能相信什么？
6. 最终是否能落到 `Continue / Narrow / Stop`：继续发布、缩小为样板教程，还是因授权或证据不足停止？

如果案例最精彩的部分无法提供证据，就不要把它写成战报；把它降级为“方法样板”或“待验证假设”。

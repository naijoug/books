# 下一条安全命令梯不是测试清单，不要只写“再跑一遍”

## 问题

AI 辅助开发里，很多交接和审查会把验证写成一串测试清单：`lint`、`test`、`build`、`smoke`、`CI`。看起来完整，实际接手者仍然不知道第一步该跑什么、失败后该缩小到哪里、哪些风险已经被证明不存在。

下一条安全命令梯要解决的不是“测试够不够多”，而是“下一条命令能不能以最小成本改变判断”。它必须说明顺序、证据含义和停止条件。

## 要点

把命令梯和测试清单分开看：

| 维度 | 测试清单 | 下一条安全命令梯 |
|---|---|---|
| 出发点 | 覆盖更多检查项 | 先回答当前最大风险 |
| 顺序 | 常按工具类型排列 | 按风险、成本和可解释性排列 |
| 失败后 | 继续跑或笼统说失败 | 立刻 Narrow 到更小证据面 |
| 通过后 | 容易写成“已验证” | 只声明这一级证明了什么 |
| 交接价值 | 接手者还要自己判断 | 接手者知道下一步、升级条件和停止条件 |

写命令梯时先问三个问题：

1. **当前最大风险是什么？** 是链接断了、状态分支错了、schema 不兼容，还是 dirty workspace 混入了未知归属？
2. **哪条命令最便宜地回答这个风险？** 不是最短命令，而是最能改变判断的命令。
3. **失败后是否会改变计划？** 如果失败后仍然只是“再跑完整测试”，它就不是命令梯。

## 示例

一个文档站改动的普通测试清单可能写成：

```text
- run lint
- run docs build
- run CI
```

更好的命令梯写法是：

```text
变更类型：VuePress 文档新增文章和 README 链接
当前最大风险：新增相对链接或 frontmatter 破坏构建

1. git -C docs diff --check -- documents/trending/ai/new-article.md documents/trending/ai/README.md
   - Pass：排除本轮 touched files 的空白、冲突标记和基础 diff 风险。
   - Fail：先修本轮文件，不进入构建。

2. 用脚本或人工检查新增相对链接目标存在
   - Pass：读者从 README 能到达新文章。
   - Fail：Narrow 到路径、文件名或目录入口。

3. cd docs/web/vuepress && npx -y pnpm@8.15.9 run docs:build
   - Pass：frontmatter、路由和 VuePress 集成链路通过。
   - Fail：记录真实 warning/error，只改本轮引入的问题；若失败来自既有噪声，显式交接。
```

同样是三步，区别在于每一步都说明“为什么先跑、通过能相信什么、失败后怎么缩小”。这让审查报告从“建议补测试”变成“下一步可执行”。

## 坑

- **把全量 CI 放第一步**：全量失败后常常只得到更大的噪声，无法知道本轮最可能风险在哪里。
- **只列命令不列含义**：接手者不知道通过后能相信什么，也不知道失败后要不要继续升级。
- **把通过说成全部安全**：focused test 通过只证明特定分支，不代表浏览器交互、生产配置或外部服务都安全。
- **忽略停止条件**：遇到未归属 dirty workspace、缺密钥、生产副作用时，继续跑命令可能扩大风险。
- **失败不改计划**：命令梯的价值在分叉；如果失败输出没有改变范围、顺序、目标或交接，它只是清单。

## 检查

写完一段验证建议后，用这 5 个问题复核：

1. 第一条命令是否直接对应当前最大风险？
2. 它是否比完整构建、全量测试或远端 CI 更便宜且更能定位？
3. 每一步是否写清 `Pass means` 和 `Fail means`？
4. 是否写出升级条件和停止条件，而不是默认一路跑到底？
5. 最终交接是否包含 `Continue / Narrow / Stop`，并把未验证项留给下一轮？

如果答不上第 1 或第 3 个问题，不要继续加测试项；先重写风险判断和 pass/fail 语义。

# 交付预算防止心跳漂移，不要把节拍用成工具维护循环

**问题**：周期性唤醒的 Agent 明明每轮都有规划、验证和提交，为什么几小时后仍可能只是在维护同一套 checker、preflight 或 notebook 模板，而没有推进真正的项目、书稿、技能或收入实验？

**要点**：

- 每轮规划时先给候选任务标出交付预算：`15 分钟`、`30 分钟`、`45 分钟` 或 `超过本轮`，预算必须对应一个可验证完成物。
- 工具维护只能服务当前最大风险：如果上一轮已经把 proof、exclusion、list-files、preflight 文档补齐，本轮默认切换到使用这些工具交付内容，而不是继续扩工具。
- 候选任务至少分成三类：项目/产品推进、内容资产、验证/流程改进；连续两轮都选同一类时，第三轮必须写出不切换的证据理由。
- 选择理由要包含“为什么现在做”而不是只写“能验证”：可验证是门槛，不是价值本身。
- 收尾时把下一轮第一条动作写成具体命令或文件，而不是“继续优化流程”。

**示例**：

```text
当前状态：上一轮给 markdown proof 加了 --list-files，并更新了 changed-from preflight。
候选：
1. 继续给 checker 加 JSON 输出。预算 45 分钟；风险是继续工具循环。
2. 给 AI Agent 书稿补一张交付预算卡。预算 30 分钟；完成物是正式卡片 + 索引计数 + verifier。
3. 回到 OpenClaw 发布。预算超过本轮；缺渠道授权。

本轮选择：2。
选择理由：上一轮工具已足够支持本轮验证；现在更高价值是把“不要在工具循环里漂移”的判断沉淀成书稿资产。
下一段第一条动作：运行 `python3 scripts/verify_tech_cards.py --full-only`，再提交 books 和 summaries。
```

**反例 / 修正做法**：

```text
反例：
- 连续四轮都在给同一个 checker 增加小开关：--exclude、--list-files、--json、--summary。
- 每轮都能通过测试，但最终没有新的文章、书稿、技能、项目功能或收入实验推进。

修正：
- 把 checker 当前能力标记为“足够支持下一次内容交付”。
- 下一轮必须选一个非 checker 的小完成物，例如一张书稿卡片、一个教程入口、一个技能样例或一个已授权发布动作。
- 如果确实还要改 checker，先写出当前失败输出如何阻断本轮交付；没有阻断证据就停止扩展。
```

**坑**：

- 把“可验证”误当“值得做”：很多工具小改都可验证，但不一定是当前最有价值的资产推进。
- 只按低风险排序，导致永远选择局部脚本和模板，而不是触达项目、内容或商业化目标。
- 下一段计划写成抽象方向，例如“继续完善验证体系”，下一轮无法直接执行。
- 没有记录连续选择同一类任务的次数，导致心跳在同一个子系统里打转。

**检查**：本轮 notebook 是否能回答三个问题：这次交付预算是多少、为什么不继续扩上一轮工具、下一轮第一条可执行动作是什么？如果任一问题答不出来，说明心跳仍有漂移风险。

# 上下文工程是状态设计，不是把材料拼成长提示

**问题**：为什么说 Agent 的上下文工程，本质上是在设计状态，而不是写更长的 prompt？

**要点**：

- 上下文应该区分“长期身份”“用户偏好”“项目事实”“本轮任务”“工具结果”“未验证假设”等状态层。
- 每一层都要有来源、更新时间、失效条件和写回位置，否则模型无法判断哪些内容能作为事实使用。
- 好的上下文工程会减少重复解释，让 Agent 能在当前事实、历史记忆和本轮目标之间做出可审计选择。

**示例**：

```text
长期身份：稳定原则，低频更新，写入 SOUL.md
用户偏好：表达、边界和交付格式，写入 USER.md
项目事实：repo 状态、文件结构、测试结果，运行时读回
本轮任务：目标、约束、候选方案和停止条件，写入当天 notebook
工具结果：命令输出、diff、hash、错误摘要，随任务记录
未验证假设：必须标注置信度和下一步验证命令
```

**坑**：只把更多片段塞进同一个提示，会让长期原则、临时计划、旧工具输出和当前事实互相污染。

**反例 / 修正做法**：

- 反例：为了让 Agent “记住一切”，把用户偏好、三个月前的产品想法、最近一次 `git status --short`、测试失败日志和本轮候选任务全部拼进 `SYSTEM_PROMPT.md`。下一次运行时，模型把过期的 git 状态当成事实，把已完成的产品想法当成当前任务，还无法判断哪些日志需要重新验证。
- 修正：把上下文当成状态表来设计：稳定层只保存长期规则；项目事实运行时用工具读回；本轮任务写入 `summaries/hermes/YYYY-MM-DD.md`；工具结果只跟随对应任务保存；未验证假设必须带 `confidence`、`source` 和 `next_check`。组装 prompt 时只加载本轮决策需要的状态，并在任务结束后把新事实写回正确位置，过期状态则显式归档或丢弃。

**检查**：如果一段上下文说不清“它属于哪一层、何时更新、何时失效、完成后写回哪里”，它就还不是可靠状态，只是提示噪音。

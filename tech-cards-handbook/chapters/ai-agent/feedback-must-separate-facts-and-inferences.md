# 反馈必须区分事实和推断，不要把感觉当结论

**问题**：Agent 收到用户反馈、测试输出或线上现象后，如何避免把零散信号过度解释成错误结论？

**要点**：

- 先记录可观察事实：谁说了什么、命令输出什么、哪个文件哪一行变化、哪一步失败。
- 再写推断：这些事实可能意味着什么；推断必须标注置信度和待验证点。
- 决策只能基于“事实 + 已验证推断”，不要只因为一个主观感受就重写产品、改架构或调整路线。
- 如果反馈来自人，保留原话摘要和场景；如果反馈来自工具，保留命令、退出码和关键输出。

**示例**：

```text
事实：
- 用户 A 试读 `sample-pack-v0.1.md` 后说：“卡片短，但我不知道怎么放进团队流程。”
- 用户 A 没有评论价格，也没有说不愿意购买。
- 3 位试读者中只有 1 位提到团队落地问题。

推断：
- 可能缺少“团队执行模板”，置信度：中。
- 不能推断“价格太高”或“所有读者都不需要卡片”，置信度：低，暂无证据。

下一步验证：
- 给下一批 3 位读者加一个问题：如果把卡片用于团队 Code Review，你还缺哪种模板？
- 只有当 3 人以上主动提到团队落地困难时，才为 v0.2 增加团队流程页。
```

**反例 / 修正做法**：

- 反例：试读者说“这张卡有点抽象”，notebook 里直接写成“用户不喜欢技术卡片，产品定位错误，下一版改成视频课”。这里唯一事实只是一个人的一句模糊评价，后面的“用户不喜欢”“定位错误”“改视频课”都是未经验证的推断。
- 修正：先记录事实：试读者身份、原话、读到的文件、是否完成任务、是否愿意继续试读；再写推断：可能缺少使用场景或示例，置信度低到中；下一步验证是追问“哪一段抽象、你期待看到什么示例”，并在至少 3 位目标读者出现同类事实后，才考虑修订 `books/tech-cards-handbook/chapters/ai-agent/` 的卡片模板。

**坑**：

- 把单个读者的“有点抽象”直接解释成“整套产品定位错误”。
- 看到一次测试失败就重构大块代码，而不是先定位失败输入、环境和复现步骤。
- 在 notebook 或交接里只写“反馈不好”，不保留原始信号，导致下一轮无法复核。
- 把自己希望发生的商业结论写成事实，例如“用户愿意付费”，但没有价格询问或付款动作。

**检查**：每条反馈至少能分成三行：`事实`、`推断`、`下一步验证`。如果某个结论找不到对应事实，先不要进入产品修订或架构修改。

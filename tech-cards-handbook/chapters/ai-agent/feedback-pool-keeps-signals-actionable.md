# 反馈池要把信号留成可执行字段

**问题**：Agent 项目、内容产品或独立工具在试用后会收到很多零散反馈：一句吐槽、一次报错、一段聊天记录、一个下载数据。若只把它们堆成“反馈列表”，下一次复盘时很难判断该修订、继续观察还是丢弃。

反馈池的目标不是收集更多声音，而是把每个声音拆成能被验证和接力的字段。

**要点**：

- 每条反馈至少记录：来源、事实、推断、影响范围、置信度、当前分级、下一步动作。
- `事实` 写可观察内容，例如原话、截图、日志、复现步骤或数据；不要写“用户不喜欢”。
- `推断` 写你对事实的解释，并标注置信度；低置信度推断只能进入观察或验证，不能直接触发重写。
- `当前分级` 沿用反馈门槛：记录、观察、验证、修订。
- `下一步动作` 必须是可执行动词：补问一个问题、复现一个步骤、改一段说明、加一个测试、联系同类用户确认。

**示例**：

```markdown
| 字段 | 内容 |
|---|---|
| 来源 | 第 3 位试读者，2026-05-20 |
| 事实 | 读到“工具结果必须可观察”后问：失败时要不要返回日志全文？ |
| 推断 | 卡片没有说明“摘要 + 证据链接”的边界，可能导致读者以为必须暴露所有日志。置信度：中 |
| 影响范围 | `tool-result-must-be-observable.md`，也可能影响 Agent 调试模板 |
| 当前分级 | 验证 |
| 下一步动作 | 再问 2 位读者是否有同样疑问；若重复出现，在“坑”里补一条日志脱敏边界 |
```

如果反馈池服务代码项目，可以把 `事实` 换成最小复现、错误日志、环境版本，把 `下一步动作` 换成失败测试或修复 PR。

**反例 / 修正做法**：

- 反例：反馈池里连续新增 20 条“用户说太复杂”“想要更自动化”“以后可以商业化”，但没有来源、原话、场景、影响范围和下一步动作。下一轮只能凭印象把它们合并成“重做产品定位”，既无法确认哪些来自目标用户，也无法判断该观察、验证还是修订。
- 修正：把每条反馈先写成字段卡：`来源`、`事实`、`推断`、`影响范围`、`置信度`、`当前分级`、`下一步动作`。例如“第 3 位试读者问失败时是否要返回日志全文”进入 `验证`，下一步是再问 2 位读者；只有重复出现或能复现业务影响时，才升级为修改 `tool-result-must-be-observable.md` 的修订任务。

**坑**：

- 把推断写进事实字段，后续会把未经验证的解释当成证据。
- 只记录“要优化”“用户不满意”，没有来源和下一步动作，下一轮无法接力。
- 每条反馈都立刻变成 todo，会让路线被噪音牵引。
- 只保留正面反馈，会错过能提升转化率、复用性或稳定性的关键信号。

**检查**：

- 随机抽一条反馈，别人只看字段能否复核原始信号？
- 是否能明确说出它现在是记录、观察、验证还是修订？
- 下一步动作是否能在 30 分钟内开始执行？
- 若今天不处理，未来接手者是否仍能知道该反馈为什么重要？

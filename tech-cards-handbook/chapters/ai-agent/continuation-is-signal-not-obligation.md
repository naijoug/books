# 接力点是信号，不是义务

**问题**：上一轮 Agent 已经写了“后续接力”，下一轮是否必须照做？

**要点**：

- 接力点是优先检查的信号，不是自动执行的命令；新一轮仍要重新评估风险、收益和验证成本。
- 先问三件事：这件事是否仍然有价值？能否缩成一个低风险小块？本轮能否验证完成？
- 如果答案不满足，最多尝试缩小一次；仍然过大，就明确切换到更小、更可验证的工作，并在记录中写清切换理由。
- 如果接力 repo 从 clean 变成未知 dirty，先判定所有权；没有证据时用 `Switch` 找 clean replacement，而不是把接力建议当接管授权。
- 不要因为“上次说了”而把短节拍拖成重构，也不要因为“不想做”而无证据地丢掉接力点。

**示例**：

```text
上一轮接力：给日志过滤增加 next/prev 跳转。
本轮评估：需要当前匹配索引、DOM refs、滚动定位和键盘语义，验证成本超过本轮节拍。
缩小尝试：只做命中总数已经完成；继续缩小会变成提示文案，收益不足。
决策：暂停 UI 跳转，改为沉淀接力点取舍规则。
后续接力：若之后有完整 UI 时间，再从滚动定位设计开始。
```

遇到接力 repo 的状态已经变化时，记录要更像一张 ownership receipt：

```text
上一轮接力：继续 `study-buddy/frontend/web` 的教材卡交互测试。
启动快照：`study-buddy/` 出现 `M frontend/shared/...`、`M frontend/web/...`、`?? frontend/web/...test.tsx`，且不全是上一轮 owned paths。
所有权证据：unknown；没有用户授权，也没有当前轮产生这些 diff 的证据。
决策：Switch 到 clean 的 `docs/` 或 `books/` 小切片；本轮不运行会改写该 repo 的 format/build 命令。
回归条件：下一轮看到 `study-buddy/` clean，或用户明确说明这些 dirty path 可接管，再回到交互测试。
```

这个写法把“为什么没有继续”变成可复查判断，而不是逃避工程任务。

**反例 / 修正做法**：

```text
反例：
上一轮说“继续做日志面板 next/prev 跳转”，所以本轮直接改滚动定位、快捷键和匹配索引；
跑不通时又继续调 CSS，因为“这是接力任务”。

修正：
先把接力点当作信号重新评估：next/prev 跳转需要 DOM refs、当前匹配索引、键盘语义和滚动验证，
超过本轮节拍。缩小一次后选择只在 `loom/src/components/Workspace/DebugPane.tsx` 增加“匹配总数”展示，
用 `git diff --check` 和最小 UI 检查验证；完整跳转设计另写为后续接力，而不是本轮硬做。
```

**坑**：

- 把交接当成待办队列，机械执行，导致小任务逐步膨胀。
- 把上一轮 clean 状态当成本轮授权，忽略启动快照里新增的 unknown dirty path。
- 只写“本轮不做”，但不说明价值、风险、验证成本，未来仍会反复纠结。
- 频繁切换目标，却没有完成任何可提交的小块。

**检查**：记录里能否同时看到“为什么优先看这个接力点”“启动快照是否支持继续”“为什么本轮执行、缩小或切换”？如果只剩结论，没有取舍过程和所有权证据，就还没有真正完成接力判断。

# 证据请求不是完整审查，不要把取证当交付

## 问题

AI 编程审查的早期对话里，最容易把“请你补一点证据”误写成“我已经开始审查”。一旦样本提供者只给了失败截图、agent 总结或一句“CI 挂了”，Agent 如果立刻承诺定位根因、修复代码或给完整报告，就会把证据不足的线索包装成交付，后续既难验证，也容易泄露不该公开的项目细节。

证据请求的目标不是证明你已经有结论，而是把模糊痛点收窄成可复核输入：原始命令、exit code、失败摘要、agent 结论和改动范围。需要可直接发送的话术时，先用 `docs/documents/trending/ai/ai-coding-audit-evidence-request-template.md`；拿到证据后，再决定进入首份报告、继续收窄，还是停止。

## 要点

- **先声明范围**：证据请求只是在判断是否适合 30–60 分钟只读审查，不承诺修复、根因或完整报告。
- **要原始证据，不要二手结论**：优先要命令、exit code、失败片段、diff 范围和 agent 原话；“它说通过了”只能作为线索。
- **每项证据都要服务决策**：拿不到命令和 exit code，就无法判断失败是否可复现；拿不到改动范围，就无法判断是否和本轮 agent 改动相关。
- **证据不足时保持 `Narrow`**：可以请求补证据，但不要把它升级为 `Continue`、案例、技能或付费承诺。
- **保护公开边界**：请求里明确允许打码仓库名、客户名、绝对路径和 token；公开材料只能来自已脱敏事实。

## 示例

```text
当前线索：
- 痛点原话："AI 说 lint 过了，但 CI 还是失败。"
- 现有证据：一段 agent summary；没有原始命令、exit code 或 diff。
- 当前决策：Narrow。

证据请求：
1. 失败命令：请贴出 CI 或本地实际运行的命令。
2. Exit code：请保留退出码，或贴出 CI job 的失败状态。
3. 失败摘要：贴最短可定位的报错片段，敏感路径可打码。
4. Agent 结论：贴 agent 当时声称通过的原文或最终报告句子。
5. 改动范围：贴本轮涉及文件列表或脱敏 diff 摘要。

收到后再判断：
- Continue：五项证据足以做只读审查。
- Narrow：缺关键命令或 diff，只请求下一项证据。
- Stop：对方只能提供截图/转述，且不允许补充可复核材料。
```

## 坑

- **请求写得像报价单**：一上来写“我会帮你定位根因并给修复建议”，会把取证阶段伪装成交付阶段。
- **只要截图**：截图可以帮助理解上下文，但不能替代命令、exit code、失败摘要和改动范围。
- **把 agent summary 当事实**：agent 的“已验证通过”是待审查对象，不是审查证据本身。
- **没有打码边界**：不提醒对方脱敏路径、客户名、token，会降低样本提供意愿，也增加公开复盘风险。
- **证据一缺就扩大范围**：缺证据时应该收窄下一条请求，而不是改成“我直接看整个 repo”。

## 检查

发送证据请求前，确认它只请求最小可复核材料，没有承诺修复或根因；五项证据都能映射到后续 `Continue / Narrow / Stop` 决策；允许对方脱敏敏感信息；写清 `Next evidence needed`；并且如果对方仍无法提供原始命令、exit code 或改动范围，你会停止或继续收窄，而不是把线索包装成完整审查。

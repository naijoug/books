# 阻断原因先做索引，不要继续扩模板

## 问题

Agent 做发布评审、AI 编程审查或上线门禁时，很容易在遇到新风险后继续新增表单：一张 warn/block 判断表、一张回滚清单、一张会后交接、一张发布说明。表单越来越多，但真正阻断交付的原因仍散落在正文、检查清单和最终报告里，下一轮只能重新阅读所有材料。

这张卡解决的问题是：当团队已经有多个评审资产时，先把“为什么被阻断”做成可搜索、可复核、可回到证据的索引，而不是继续新增同类模板。

## 要点

1. **阻断原因是检索入口，不是结论口号**：索引条目要写成“缺少 rollback owner”“warn 被包装成 block 例外”“验证输出不可移植”这类可定位问题，而不是“发布风险较高”。
2. **每条原因必须指向证据字段**：至少包含来源资产、字段名、触发条件和下一步动作；否则索引只是另一份散文总结。
3. **先覆盖高频阻断，不追求完整 taxonomy**：从最近三到五次评审里反复出现的阻断原因开始，先让下一轮能快速命中，而不是先设计庞大的分类树。
4. **索引要连接模板而不复制模板**：条目指向发布报告、门禁表、交接字段或样例，不在索引里重写完整表单，避免两份口径漂移。
5. **每次新增原因要有退出条件**：如果一条原因没有真实案例、没有字段来源、没有下一步动作，先写入待观察池，不进入正式阻断索引。
6. **用索引反推资产缺口**：连续多次命中同一阻断原因但下游没有固定字段时，再补模板字段；不是每次新风险都立刻扩表面。

## 示例

一次 Agent 发布评审后，不要马上新增“发布风险复盘模板”，先把阻断原因压成索引条目：

```text
阻断原因：rollback owner 不明确
来源资产：第 9 章发布报告 / 附录 C 会后交接
字段：rollback_owner, rollback_runbook, next_review_trigger
触发条件：报告写了可回滚，但没有具体 owner 或第一条回滚命令
下一步动作：补 owner 与 runbook；复审前不得把结论从 block 改成 warn
证据位置：发布报告字段 + 会后交接片段
```

再补一条验证类阻断：

```text
阻断原因：验证输出不可移植
来源资产：proof checker 一页纸 / 最终报告字段速查
字段：verification_command, portable_output, unverified_boundary
触发条件：notebook 或 final report 只写本机绝对路径、截图、或“已通过”而无可复制命令
下一步动作：重跑可复制命令；把输出压缩为 repo 相对路径和关键行
证据位置：proof 输出 + final report 摘要
```

这两个条目已经能让下一轮快速判断“该补证据、补 owner，还是保持 block”。只有当某个条目连续命中却没有字段承接时，才新增或调整模板。

## 坑

- **把索引写成 FAQ**：问答可读，但缺少字段、触发条件和下一步动作，无法驱动发布判断。
- **按资产分组而不是按阻断原因分组**：读者还是要先知道该看哪份模板；索引没有成为入口。
- **复制整张模板**：索引和模板出现两份字段定义，下一次只会同步其中一份。
- **没有真实命中记录**：为了“看起来完整”提前列 30 类风险，维护成本超过使用价值。
- **忽略降级路径**：有些原因只需要 Narrow 或待观察，不一定全部 block；索引要写清何时 Continue / Narrow / Stop。

## 检查

提交阻断原因索引前，逐项确认：

- 每条索引是否以具体阻断原因命名，而不是以模板名或章节名命名？
- 是否写清来源资产、字段名、触发条件、下一步动作和证据位置？
- 是否至少来自一次真实评审、发布、审查或 cron 接力，而不是预设 taxonomy？
- 是否只链接到模板字段，不复制整张模板？
- 是否能帮助下一轮在 3 分钟内判断 Continue / Narrow / Stop？
- 若命中同一原因三次以上，是否反向检查下游模板是否缺字段，而不是继续堆索引条目？

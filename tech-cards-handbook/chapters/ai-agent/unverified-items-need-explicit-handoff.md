# 未验证项要显式交接，不要藏在顺利总结里

**问题**：Agent 已经做完一部分工作，但仍有构建、人工交互、线上效果或边界条件没有验证时，怎样交接才不会让下一轮误以为任务已经完全闭环？

**要点**：

- 未验证项不是失败，但必须可见；如果报告只写顺利进展，下一轮会把缺口当成已完成事实。
- 每个未验证项都要绑定原因和下一步：为什么没验证、从哪里开始补验证、什么结果算通过。
- 把“未验证”写成可执行清单，而不是模糊免责声明，例如不要只写“有待进一步测试”。
- 如果未验证项会改变结论，就降低措辞强度：从“已修复”改成“已修改并通过静态检查，仍需手工验证交互”。

**示例**：

```text
不好的交接：
- 已完成日志搜索体验优化，后续可以继续完善。

更好的交接：
- 已修改 `loom/src/components/Workspace/DebugPane.tsx`，日志过滤命中词会高亮，并显示 match 数量。
- 已验证：`npm run build`、`cargo check --manifest-path src-tauri/Cargo.toml`、`git diff --check` 均通过。
- 未验证：没有在真实 UI 中手工点击多条 run 的日志过滤；原因是本轮没有启动桌面应用。
- 下一步：启动 Loom，选择包含 stdout/stderr 的 run，输入大小写不同的过滤词，确认高亮和 match 数量一致。
```

**反例 / 修正做法**：

```text
反例：
- 已完成构建脚本修复，整体可用；后续有空再跑一下完整测试。

问题：
- “整体可用”暗示已经闭环，但完整测试其实没有跑。
- 没写为什么没跑，也没写从哪个命令开始补验证。
- 下一轮不知道失败会影响“已修复”还是只影响边界场景。

修正：
- 已修改 `scripts/build-release.sh`，并通过 `shellcheck scripts/build-release.sh`。
- 未验证：`npm run build` 没有执行；原因是当前工作区已有非本轮前端改动，直接跑全量构建会混入不相关失败。
- 下一步：在干净分支或确认前端改动归属后运行 `npm run build`；若失败，把结论降级为“脚本已静态检查通过，尚未证明发布构建可用”。
```

**坑**：

- 把未验证项放进“后续优化”里，导致它听起来像增强需求，而不是当前结论的证据缺口。
- 只写“未充分测试”，但不说明缺少哪类测试、为什么缺、下一步怎么补。
- 为了让总结更好看，省略失败命令或无法验证的外部依赖。
- 把低成本可验证项也留给下一轮；显式交接不是逃避验证，能当场验证的先验证。

**检查**：读完交接后，下一轮 Agent 应该能直接列出“可信结论”和“仍需确认的结论”。如果未验证项会影响用户是否能放心使用，就必须在总结中单独列出，并给出第一条补验证动作。

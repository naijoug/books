## 阅读建议

1. 新手按章节顺序阅读，先建立 Agent 的基本概念和设计原则。
2. 已有开发经验的读者可以从第 4-7 章进入架构和工具集成。
3. 准备上线生产系统时，重点阅读第 8-10 章，并按“测试集与评估报告字段 → 发布监控与灰度报告 → 安全门禁 → 熔断恢复”的顺序落地。

## 生产上线阅读路径

- 第 7 章：确认工具注册、工具描述、执行沙箱、权限边界、工具路由和供安全回归/发布门禁使用的工具安全元数据。
- 第 8 章：把关键任务写成 Golden Tasks，覆盖成功路径、失败路径、权限测试、敏感字段扫描和可进入发布门禁的安全回归集；评估报告需要沉淀 `run_id`、版本字段、`gate_decision`、`failed_case_ids`、`safe_trace_links`、`audit_event_ids` 等共享字段，进入第 9 章发布报告时再补齐 `release_id`。
- 第 9 章：建立部署、监控、告警、只读灰度 / 人工审批灰度、回滚和成本止损机制，并把第 8 章的评估报告、失败样本 ID、脱敏执行 trace 与审计事件接入同一条发布流水线；发布报告中的灰度范围、禁用工具、回滚开关、`safe_trace_links` 和 `next_review` 应能直接回填附录 A/B/C。
- 第 10 章：补齐 Prompt 注入防御、数据脱敏、人工审批、脱敏执行 trace、审计日志、事故熔断 runbook 与发布前安全检查清单；安全门禁报告应直接引用第 8 章产出的评估证据。

如果时间有限，可以把这条路径压缩成一次 90 分钟上线前审查：先列工具风险表，再跑最小 Golden Tasks，然后补发布报告和安全门禁结论，最后只在证据链完整时开放灰度。根目录 `README.md` 中的“90 分钟上线前审查工作流”给出了时间盒、最小产物和一张材料选择表：第 7 章回答工具边界，第 8 章回答测试证据，第 9 章回答灰度止损，第 10 章回答硬阻断风险，附录 C 回答会后谁接手。附录 A 可作为空白核对表，附录 B 可作为填完后的门禁报告参考，并用反例提醒团队不要把缺失硬边界的 `block` 写成“后续优化”的 `warn`；附录 C 则提供主持人脚本和会后交接填写样例，帮助发布 owner 在 30～60 分钟会议里把讨论收束为允许范围、禁用范围、证据缺口、下一次复审条件和下一步可执行命令。

进入第 7-10 章和附录 A/B/C 前，先沿用根目录 `README.md` 的统一术语口径：服务端确定性边界统一叫“工具网关”；长期评审材料只引用 `safe_trace_links`；`restricted_trace` 只做短期审批访问；只读灰度不开放写副作用；人工审批灰度要求审批绑定工具名、参数快照、`args_hash`、资源范围、幂等键和过期时间；`warn` 只能用于硬边界已存在但范围受限的情况，缺少权限、脱敏、审计或回滚硬边界时必须写成 `block`。第 10 章的服务端权限检查段落已反链根 README 的术语表，可作为评审会上解释“工具网关不是只做鉴权”的正文入口。

### 按角色快速定位附录

- 发布 owner：从附录 A 开始，确认 `release_id`、工具 allowlist、禁用范围、灰度边界和会前材料是否齐全，再用附录 C 主持评审。
- Agent 开发者：重点看附录 A 的工具 / 评估 / trace 字段和附录 B 的填写样例，确保 Golden Tasks、失败样本、脱敏 trace、审计事件可以追溯。
- 安全 reviewer：先看附录 B 的 `warn` 样例与 `block` 反例，判断缺失项是可受控风险，还是缺少审批、回滚、审计、安全回归等硬边界。
- 值班 / SRE：使用附录 C 的监控、止损、回滚、发布报告字段映射和会后交接清单，确认下一班能按命令、告警和复审触发条件接手。
- 业务负责人：阅读附录 C 的 30 分钟脚本和最终结论段，确认用户范围、人工兜底、禁用能力和业务影响表达清楚。

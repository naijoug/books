# AI 程序员可验证交付模板包

> 草稿用途：承接 `ai-programmer-verifiable-delivery-loop.md`，为《AI 时代个人提升指南》的附录候选内容提供可直接复用的任务卡、风险清单、验证记录和复盘模板。当前先放在 `.drafts/`，不直接并入正式章节；后续并入 `chapters/appendix.md` 前，需要先分诊附录已有 dirty diff。

## 使用原则

这组模板不是为了增加流程负担，而是为了让人和 AI 的协作具备三个特征：

1. **边界清楚**：AI 知道能看什么、能改什么、不能碰什么。
2. **证据可查**：完成不是一句“应该可以”，而是有命令、日志、截图、diff、人工复核或用户反馈。
3. **经验可复用**：一次交付结束后，至少沉淀一个下次能复用的字段、脚本、清单或判断标准。

如果任务小，可以只填关键字段；如果涉及发布、资金、用户数据、线上配置或跨 repo 提交，必须完整填写。

## 模板一：AI 协作任务卡

```text
任务名称：

为什么值得做：
- 它解决的真实问题是什么？
- 如果不做，会继续产生什么成本或风险？

本轮只做什么：
- 本轮最小可交付结果：
- 成功后可观察到的变化：

明确不做什么：
- 不改动的模块 / 文件：
- 不触发的外部动作：
- 不做的产品 / 发布 / 运营动作：

AI 可读取的资料：
- 需求 / issue / 文档：
- 相关代码 / 测试 / 日志：
- 已脱敏的样例数据：

AI 可修改的范围：
- 允许修改的文件或目录：
- 允许新增的文件类型：
- 提交时只允许纳入的路径：

禁止动作：
- 不删除用户或其他 agent 的未提交改动。
- 不自动 push、发布、发邮件、调用付费 API 或修改生产配置。
- 不把本机绝对路径、密钥、token、隐私数据写入文档或日志。

验收证据：
- 必须运行的命令：
- 必须人工检查的页面 / 文档 / diff：
- 必须保留的输出或截图：

失败回退：
- 如果测试失败，先停在哪里：
- 如果发现边界不清，找谁确认：
- 如果需要回滚，回滚哪些文件：

本轮沉淀资产：
- 模板：
- 脚本：
- 文档：
- 测试 / fixture：
- 复盘记录：
```

## 模板二：让 AI 先给风险清单的提示词

```text
请先不要修改文件。基于下面的任务卡，输出一份执行前风险清单：

1. 你理解的目标和非目标分别是什么？
2. 哪些文件、命令或外部动作最容易越界？
3. 动手前必须先读取或确认哪些上下文？
4. 最小实现路径是什么？请拆成 1-3 个小步骤。
5. 每一步分别用什么证据验证？
6. 哪些判断必须由人确认，不能由你自动推断？
7. 如果发现已有未提交改动，你会如何避免混入？

任务卡：
[粘贴任务卡]
```

判断这份风险清单是否合格，可以看它有没有主动指出“不能做什么”。如果 AI 只给实现方案、不提禁止动作、验证证据和人工确认点，说明它还没有进入可信交付状态。

## 模板三：执行中小步验证记录

````text
当前步骤：

改动范围：
- 新增：
- 修改：
- 删除：

为什么这是最小步：

验证命令：
```bash
[命令]
```

实际输出摘要：
- 通过：
- 失败：
- 需要人工复核：

本步产生的新风险：

是否继续下一步：
- [ ] 继续，因为证据满足预期
- [ ] 暂停，因为需要补上下文
- [ ] 回滚，因为超出边界或验证失败
````

这个模板特别适合用于 Agent 任务中途复盘。它能防止“连续改了很多文件之后才发现验证入口不对”的情况。

## 模板四：交付前验收清单

| 检查项 | 问题 | 证据 |
|---|---|---|
| 范围 | 是否只改了任务卡允许的文件？ | `git status --short`、路径列表 |
| 差异 | diff 是否只包含本轮意图内改动？ | `git diff -- ...` 或人工 diff review |
| 语法 | 代码 / 配置 / Markdown 是否有明显语法问题？ | 语言编译、lint、markdown 检查 |
| 行为 | 核心功能是否用测试或最小 fixture 跑过？ | 测试命令和输出 |
| 失败分支 | 关键失败路径是否被验证？ | 负向测试、错误信息、门禁输出 |
| 边界 | 是否避免 push、发布、外发、生产配置等高风险动作？ | 命令记录、环境变量检查 |
| 文档 | 文档是否使用相对路径，且没有泄漏本机环境？ | 人工检查、搜索绝对路径 |
| 提交 | 是否只 stage 本轮相关文件？ | `git diff --cached --name-only` |
| 接力 | 下一步是否具体到一个可执行小任务？ | notebook、run note 或 issue |

### 附录：AI 程序员可验证交付任务卡

AI 时代的程序员不只是“会让模型写代码”，更重要的是能把一次协作变成可检查、可复用、可交接的交付过程。下面这套三件套适合用于功能开发、文档整理、发布准备、自动化脚本和 Agent 任务编排。

#### 1. 任务卡：先圈定边界

```text
任务名称：

本轮最小目标：
- 只完成：
- 不处理：

AI 可读取的上下文：
- 需求 / 文档：
- 相关代码 / 测试：
- 已脱敏样例：

AI 可修改的范围：
- 允许修改：
- 允许新增：
- 提交时只 stage：

禁止动作：
- 不删除或覆盖未接管改动。
- 不自动 push、发布、外发、调用付费 API 或修改生产配置。
- 不写入本机绝对路径、密钥、token 或隐私数据。

验收证据：
- 命令：
- 日志 / 截图 / diff：
- 人工复核点：

失败回退：
- 失败先停在哪里：
- 需要谁确认：
- 回滚哪些文件：
```

#### 2. 风险清单提示词：先让 AI 暂停

```text
请先不要修改文件。基于下面的任务卡，输出执行前风险清单：

1. 你理解的目标和非目标是什么？
2. 哪些文件、命令或外部动作最容易越界？
3. 动手前必须先读取哪些上下文？
4. 最小实现路径是什么？请拆成 1-3 步。
5. 每一步用什么证据验证？
6. 哪些判断必须由人确认，不能由你自动推断？
7. 如果发现已有未提交改动，你会如何避免混入？

任务卡：
[粘贴任务卡]
```

#### 3. 交付前验收清单：先留证据再宣布完成

| 检查项 | 必问问题 | 证据 |
|---|---|---|
| 范围 | 是否只改了任务卡允许的路径？ | `git status --short`、路径列表 |
| 差异 | diff 是否只包含本轮意图？ | `git diff -- ...` 或人工 review |
| 语法 | 代码、配置或 Markdown 是否能被解析？ | 编译、lint、格式检查 |
| 行为 | 核心功能是否真的跑过？ | 测试命令、最小 fixture、页面检查 |
| 失败分支 | 关键阻断路径是否也验证过？ | 负向测试、错误输出、门禁日志 |
| 边界 | 是否避免发布、push、生产配置等高风险动作？ | 命令记录、环境变量检查 |
| 文档 | 是否只写相对路径且无本机环境泄漏？ | 搜索绝对路径、人工复核 |
| 提交 | 是否只 stage 本轮相关文件？ | `git diff --cached --name-only` |
| 接力 | 下一步是否具体可执行？ | notebook、issue、run note 或 TODO |

这套模板的价值不在于形式完整，而在于训练一种职业习惯：任何 AI 参与的交付，都要能说清“边界是什么、证据在哪里、失败如何停下、经验如何复用”。

## 第 10 章行动练习候选：连续 4 周训练可验证交付

> 建议并入位置：`chapters/10-30-day-action-handbook.md` 的每周行动或复盘部分。正式并入时不必完整复制模板，只保留每周节奏、交付物和复盘问题。

如果第 8 章解释的是“为什么程序员要建立可验证交付循环”，附录提供的是“任务卡怎么填”，那么第 10 章可以把它变成 30 天训练计划。目标不是一个月内掌握所有 AI 工具，而是在连续 4 周内至少完成 4 次小交付，每次都留下边界、证据和复盘。

| 周次 | 训练主题 | 最小任务 | 必须留下的证据 |
|---|---|---|---|
| 第 1 周 | 任务边界 | 选择一个真实小问题，写一张 AI 协作任务卡，只允许 AI 先给风险清单 | 任务卡、风险清单、人工删改记录 |
| 第 2 周 | 小步实现 | 让 AI 只改一个低风险文件或补一段文档，并在每一步后运行最小验证 | diff、验证命令输出、失败停点 |
| 第 3 周 | 失败分支 | 故意设计一个不能通过的输入、占位配置或越界路径，让 AI 帮你补负向测试或门禁 | 负向测试、错误信息、阻断说明 |
| 第 4 周 | 沉淀资产 | 把前三周最有价值的一张卡、一条命令或一段检查逻辑整理成模板、脚本或 SOP | 模板 / 脚本 / SOP、复盘卡、下一步任务 |

每周结束时只问 5 个问题：

```text
1. 本周的真实任务是什么？是否太大？
2. AI 的参与边界是否写清楚？有没有越界风险？
3. 我用什么证据证明结果真的可用？
4. 哪个失败分支被提前发现或阻断？
5. 下周可以复用什么资产？
```

这套练习的关键，是让“AI 帮我做了什么”变成“我如何控制 AI 参与交付”。连续 4 周后，如果你能拿出 4 张任务卡、4 组验证证据、至少 1 个失败分支和 1 个复用资产，就已经比只收藏工具教程更接近职业资产。

### 可压缩进正文的版本

```text
30 天行动的底层训练，不是每天多问 AI 一个问题，而是每周完成一次可验证交付闭环：

第 1 周：写清任务边界，让 AI 先给风险清单，不急着改文件。
第 2 周：选择一个低风险小任务，让 AI 小步实现，并在每一步留下验证命令或人工复核证据。

```

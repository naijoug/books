# AI 程序员可验证交付模板包

> 草稿用途：承接 `ai-programmer-verifiable-delivery-loop.md`，为《AI 时代个人提升指南》的附录候选内容提供可直接复用的任务卡、风险清单、验证记录和复盘模板。当前先放在 `.drafts/`，不直接并入正式章节；后续并入 `chapters/appendix.md` 前，需要先分诊附录已有 dirty diff。

## 使用原则

这组模板不是为了增加流程负担，而是为了让人和 AI 的协作具备三个特征：

1. **边界清楚**：AI 知道能看什么、能改什么、不能碰什么。
2. **证据可查**：完成不是一句“应该可以”，而是有命令、日志、截图、diff、人工复核或用户反馈。
3. **经验可复用**：一次交付结束后，至少沉淀一个下次能复用的字段、脚本、清单或判断标准。

如果任务小，可以只填关键字段；如果涉及发布、资金、用户数据、线上配置或跨 repo 提交，必须完整填写。

## 模板一：AI 协作任务卡

```text
任务名称：

为什么值得做：
- 它解决的真实问题是什么？
- 如果不做，会继续产生什么成本或风险？

本轮只做什么：
- 本轮最小可交付结果：
- 成功后可观察到的变化：

明确不做什么：
- 不改动的模块 / 文件：
- 不触发的外部动作：
- 不做的产品 / 发布 / 运营动作：

AI 可读取的资料：
- 需求 / issue / 文档：
- 相关代码 / 测试 / 日志：
- 已脱敏的样例数据：

AI 可修改的范围：
- 允许修改的文件或目录：
- 允许新增的文件类型：
- 提交时只允许纳入的路径：

禁止动作：
- 不删除用户或其他 agent 的未提交改动。
- 不自动 push、发布、发邮件、调用付费 API 或修改生产配置。
- 不把本机绝对路径、密钥、token、隐私数据写入文档或日志。

验收证据：
- 必须运行的命令：
- 必须人工检查的页面 / 文档 / diff：
- 必须保留的输出或截图：

失败回退：
- 如果测试失败，先停在哪里：
- 如果发现边界不清，找谁确认：
- 如果需要回滚，回滚哪些文件：

本轮沉淀资产：
- 模板：
- 脚本：
- 文档：
- 测试 / fixture：
- 复盘记录：
```

## 模板二：让 AI 先给风险清单的提示词

```text
请先不要修改文件。基于下面的任务卡，输出一份执行前风险清单：

1. 你理解的目标和非目标分别是什么？
2. 哪些文件、命令或外部动作最容易越界？
3. 动手前必须先读取或确认哪些上下文？
4. 最小实现路径是什么？请拆成 1-3 个小步骤。
5. 每一步分别用什么证据验证？
6. 哪些判断必须由人确认，不能由你自动推断？
7. 如果发现已有未提交改动，你会如何避免混入？

任务卡：
[粘贴任务卡]
```

判断这份风险清单是否合格，可以看它有没有主动指出“不能做什么”。如果 AI 只给实现方案、不提禁止动作、验证证据和人工确认点，说明它还没有进入可信交付状态。

## 模板三：执行中小步验证记录

````text
当前步骤：

改动范围：
- 新增：
- 修改：
- 删除：

为什么这是最小步：

验证命令：
```bash
[命令]
```

实际输出摘要：
- 通过：
- 失败：
- 需要人工复核：

本步产生的新风险：

是否继续下一步：
- [ ] 继续，因为证据满足预期
- [ ] 暂停，因为需要补上下文
- [ ] 回滚，因为超出边界或验证失败
````

这个模板特别适合用于 Agent 任务中途复盘。它能防止“连续改了很多文件之后才发现验证入口不对”的情况。

## 模板四：交付前验收清单

| 检查项 | 问题 | 证据 |
|---|---|---|
| 范围 | 是否只改了任务卡允许的文件？ | `git status --short`、路径列表 |
| 差异 | diff 是否只包含本轮意图内改动？ | `git diff -- ...` 或人工 diff review |
| 语法 | 代码 / 配置 / Markdown 是否有明显语法问题？ | 语言编译、lint、markdown 检查 |
| 行为 | 核心功能是否用测试或最小 fixture 跑过？ | 测试命令和输出 |
| 失败分支 | 关键失败路径是否被验证？ | 负向测试、错误信息、门禁输出 |
| 边界 | 是否避免 push、发布、外发、生产配置等高风险动作？ | 命令记录、环境变量检查 |
| 文档 | 文档是否使用相对路径，且没有泄漏本机环境？ | 人工检查、搜索绝对路径 |
| 提交 | 是否只 stage 本轮相关文件？ | `git diff --cached --name-only` |
| 接力 | 下一步是否具体到一个可执行小任务？ | notebook、run note 或 issue |
